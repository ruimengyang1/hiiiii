==================================================
1. HIGH-LEVEL DESIGN GOAL
==================================================

Transform the prototype into a:

    SYSTEMIC REAL-TIME PUZZLE PLATFORMER

The main skill should NOT be:

    execute difficult jumps

The main skill should be:

    understand a small set of interacting rules,
    manipulate agents and objects,
    predict consequences,
    and plan interactions in the correct order.

A player who understands the system should perform much better than a player who simply has strong platforming reflexes.

Keep movement satisfying, but movement is the means of interacting with the system, not the entire challenge.

==================================================
2. CENTRAL FANTASY
==================================================

The current prototype contains a useful starting idea:

- player enters the level
- a barrel attacks/chases the player
- player can use the barrel as a bounce target/platform
- player reaches a cart/train car
- an NPC/person is associated with the cart
- barrel can push the cart
- the player needs to somehow get the cart/NPC to the right-side destination

Build the entire redesign around the idea:

    THE THREAT IS ALSO THE TOOL.

More specifically:

    "I do not directly control the important objects.
     I manipulate the system so that they control each other."

The player should gradually realize:

    My position controls the barrel.
    The barrel controls the cart.
    The cart changes the level state.
    The NPC changes progression.
    Hazards can affect enemies.
    Enemies can affect hazards.
    Previous interactions create new future possibilities.

==================================================
3. DESIGN INSPIRATION: I WANNA
==================================================

Use the useful design idea from I Wanna Be The Guy:

    The player's first interpretation of a situation can be wrong.

BUT:

Do NOT simply create arbitrary surprise spikes, invisible traps, or cheap deaths.

Instead use SYSTEMIC MISDIRECTION.

The structure should be:

1. Teach a rule clearly.
2. Let the player form a heuristic.
3. Present a situation where blindly applying that heuristic fails.
4. Make the failure reveal additional information.
5. On the next attempt, the player changes STRATEGY, not merely timing.

Example:

The player learns:

    "Stand to the right of the cart.
     Barrel charges right.
     Barrel pushes cart right."

Then later:

Doing exactly that immediately creates a bad state:
- cart enters danger
- useful barrel becomes inaccessible
- NPC gets stuck
- player loses the only useful route
- a hazard activates too early
etc.

The player realizes:

    "Push right" is not the full rule.

The improved heuristic becomes:

    "Before moving the cart, think about what state I need afterward."

Failures should reveal the real structure of the system.

BAD I-Wanna-style design:

    surprise spike kills player with no useful information

GOOD:

    player's reasonable strategy produces a clear,
    understandable consequence that teaches something new.

==================================================
4. DESIGN INSPIRATION: DWARF FORTRESS
==================================================

Use the useful systemic design principle:

    complexity comes from COMPOSITION,
    not from a long list of unrelated mechanics.

Do not create 15 new mechanics.

Instead create a small interaction vocabulary.

Prefer rules like:

    Barrel + Cart -> Cart moves

    Barrel + Wall -> Barrel changes direction

    Player + Barrel -> Player bounces / barrel changes state

    Barrel + Hazard -> Barrel becomes stunned / redirected / destroyed

    Enemy + Hazard -> Enemy changes state

    Projectile + Enemy -> Enemy reacts

    Cart + Switch -> Environmental state changes

    Cart + NPC destination -> progression changes

    Stunned enemy + Player -> traversal opportunity

The critical principle:

    A + B -> C
    and C should then be usable by another rule.

For example:

    Barrel hits cart
        ->
    Cart moves under upper platform
        ->
    Cart becomes traversal platform
        ->
    Player reaches switch
        ->
    Switch changes hazard
        ->
    Barrel can now travel through previous area
        ->
    Barrel pushes cart again

THIS is preferred over:

    Room 1 teaches mechanic A
    Room 2 teaches mechanic B
    Room 3 teaches mechanic C

The systems should overlap.

==================================================
5. DESIGN INSPIRATION: SYSTEMIC ZELDA-LIKE THINKING
==================================================

Use the principle that objects should have GENERAL PROPERTIES,
not only one-off puzzle scripts.

Prefer:

    charging object transfers momentum

over:

    "this barrel pushes this specific cart"

Prefer:

    heavy moving object activates pressure trigger

over:

    "when cart reaches x=850, open door"

Prefer:

    hazard damages/stuns all valid actors

over:

    "this hazard only affects player"

When reasonable, use shared interfaces / reusable functions for:

- damage
- knockback
- stun
- push
- activation
- state changes

Do not overengineer.

The purpose is to make interactions reusable enough for unexpected combinations to emerge.

==================================================
6. CORE SYSTEM: PLAYER -> BARREL -> CART -> NPC
==================================================

This should remain the strongest central interaction chain.

PLAYER POSITION
    ->
BARREL BEHAVIOR
    ->
BARREL COLLISION
    ->
CART POSITION
    ->
NPC POSITION / LEVEL STATE
    ->
NEW PLAYER OPTIONS

------------------------------
BARREL
------------------------------

Redesign the barrel into a predictable but manipulable agent.

Preferred state machine:

IDLE
    ->
NOTICE PLAYER
    ->
TELEGRAPH
    ->
LOCK DIRECTION
    ->
CHARGE
    ->
COLLISION RESULT
    ->
RECOVERY / STUN
    ->
IDLE

Important:

The barrel must NOT continuously perfectly home toward the player.

The player needs to be able to intentionally place themselves somewhere,
observe the telegraph,
and predict the barrel's path.

During telegraph:
- readable animation
- readable sound
- clear facing / direction indicator if visually appropriate

During charge:
- commit to direction
- strong momentum
- consistent collision behavior

The barrel therefore functions as a controllable environmental force.

==================================================
7. BARREL SHOULD HAVE MULTIPLE USES
==================================================

The same barrel should serve several purposes.

At minimum:

USE 1:
danger / enemy

USE 2:
bounce target for player traversal

USE 3:
push cart

Strongly consider one or two additional SYSTEMIC uses if they fit existing project systems:

USE 4:
hit / stun another enemy

USE 5:
hit a switch

USE 6:
be redirected by a wall or bumper

USE 7:
break a fragile obstacle

USE 8:
interact with an existing hazard

Do NOT implement all of these automatically.

Inspect current code and choose the 1–2 additions that create the most interesting combinations using existing systems.

==================================================
8. CART REDESIGN
==================================================

The cart should no longer feel like a passive escort prop.

Its POSITION should become part of the puzzle state.

The cart can potentially be:

- NPC transport
- movable platform
- blocker
- shield
- weight
- temporary bridge
- obstacle
- route modifier

Choose only the roles that fit the current level.

The player should sometimes want:

    cart farther right

but sometimes want:

    cart to remain here temporarily

or:

    cart at an intermediate position

This prevents:

    "always push right"

from solving the game.

Cart movement must be deterministic enough for strategy.

Avoid chaotic physics.

Use:
- controlled step movement
- constrained physics
- strong damping
- snapping to useful positions
- or another predictable method

whichever best fits the current architecture.

==================================================
9. NPC REDESIGN
==================================================

The NPC should have a clear systemic role.

Do NOT create complex companion AI unless already supported.

The NPC can primarily function as:

    OBJECTIVE + STATE KEY

For example:

NPC reaches station A
    ->
activates system

NPC reaches station B
    ->
opens final gate

NPC/cart position can visually communicate progress.

Optional:
Give the NPC simple reactions:
- scared when barrel approaches
- relief after successful move
- point / look toward destination
- react when cart nearly enters danger

This is feedback, not a dialogue system.

==================================================
BEAT 4 — BREAK THE PLAYER'S HEURISTIC
==================================================

This is critical.

By now player probably believes:

    "Use barrel to push cart right."

Create a situation where that reasonable strategy creates a bad future state.

Examples:

A.
Cart blocks the only way to reposition the barrel.

B.
Moving cart too early removes the player's bounce access.

C.
Cart enters a hazard zone before hazard has been disabled.

D.
Cart activates a crusher too early.

E.
NPC reaches intermediate trigger before player is ready.

F.
Barrel becomes trapped on wrong side.

G.
Player needs the barrel for vertical traversal before using it to move cart.

The failure should be readable.

The player should think:

    "Oh. I needed to do X first."

NOT:

    "What random thing killed me?"

This should be the main I-Wanna-inspired moment.

==================================================
BEAT 5 — SYSTEMIC PAYOFF
==================================================

Final area should use NO major new mechanic.

Instead combine previously learned relationships.

Create a situation with several relevant objects at once, such as:

PLAYER
BARREL
CART
NPC
HAZARD
ENEMY / SWITCH

The player should need to plan 3–5 interactions ahead.

Example structure:

1. keep cart in place
2. bait barrel toward upper route
3. use barrel as bounce target
4. activate environmental change
5. reposition to other side
6. bait barrel again
7. barrel pushes cart
8. cart/NPC reaches destination
9. level exit becomes accessible

There can be multiple valid solutions if the systems naturally allow them.

Do not force only one exact pixel-perfect scripted sequence.

==================================================
11. HEURISTIC PROGRESSION
==================================================

Explicitly design around learned heuristics.

Initial heuristic:

    Barrel = danger.

Then:

    Barrel can also help me move.

Then:

    Barrel can move the cart.

Then:

    My position controls the barrel.

Then:

    I indirectly control the cart.

Then:

    Do not immediately use every available interaction.

Then:

    Object state and position are resources.

Then:

    Plan the order of interactions.

The game should intentionally make some early heuristics incomplete.

Do not invalidate them randomly.

REFINE them.

Example:

Early:
    "Push cart right."

Later:
    "Push cart right when the future state will still be useful."

Treat these as meaningful resources.

MOST IMPORTANT RULE
==================================================

Do not optimize for:

    MORE CONSEQUENCES FROM THE SAME MECHANICS.
